# API الشكاوى والاقتراحات للزبائن

واجهة مستقلة عن API الموظفين، جاهزة لنموذج الزبائن المستقبلي، وتعمل دون تسجيل دخول وفق الاتفاق. تحفظ الطلب داخل جداول الشكاوى نفسها بمصدر **زبون**، وتوجهه تلقائيًا إلى جميع مديري النظام الفعّالين. لم تُضف شاشة زبائن في الموقع أو التطبيق ضمن هذا التعديل.

## الواجهات

العنوان الأساسي: `https://<API-HOST>/api/v1/customer-feedback`.

| الطريقة والمسار | الوظيفة |
|---|---|
| `GET /options` | الأنواع الفعالة والعلامات التجارية المتاحة وحقول التواصل المطلوبة وحدود الملفات. |
| `GET /options?brandID=29&typeID=1` | الواجهة نفسها، مع فروع العلامة ومواضيعها حسب النوع المحدد. `typeID=0` يعيد جميع المواضيع الفعالة للعلامة. |
| `POST /requests` | تقديم بيانات الزبون والطلب والمرفقات معًا باستخدام `multipart/form-data`. |

هذه واجهتان فقط. لا يلزم `EmployeeNumber` أو Bearer token، ولا تُقبل حقول هوية الموظف أو مصدر الطلب أو جهة المستلم من الزبون. HTTPS إلزامي. أرسل `Accept: application/json`.

## تسلسل النموذج

1. اطلب `/options` لعرض الأنواع والعلامات التجارية.
2. عند اختيار العلامة والنوع أعد طلب `/options?brandID=...&typeID=...` لعرض الفروع والمواضيع المناسبة. القائمة لا تكشف بيانات الموظفين أو أسماء مديري النظام.
3. يكتب الزبون الاسم ورقم التواصل، والبريد الإلكتروني اختياريًا، ويحدد الفرع والموضوع ويكتب عنوان الطلب وتفاصيله وخيار إظهار الهوية.
4. أرسل البيانات والملفات في طلب واحد. API يتحقق من المدخلات وتبعية الفرع للعلامة وتطابق الموضوع والنوع والعلامة وحالة التفعيل، ثم يحفظ الطلب ومرفقاته وسجل التقديم وإشعارات مديري النظام.
5. اعرض رسالة النجاح ورقم الطلب. الرقم مرجع للتواصل، ولا يمنح وصولًا عامًا إلى تفاصيل الطلب أو مرفقاته.

## البيانات المدخلة

أسماء الحقول ثابتة كما في المثال؛ `Name` و`Mobile` إلزاميان، و`Email` اختياري ويمكن حذفه أو إرساله `null`. `DiscloseIdentity` إلزامي. عند اختيار `false` تُحفظ بيانات التواصل داخل قاعدة البيانات، وتُخفى عن المستلمين كما في طلب الموظف المجهول.

لا يرسل الزبون أسماء العلامة والفرع؛ يرسل المعرفات من قائمة الخيارات، وAPI يحفظ أسماءهما بنفسه من قاعدة البيانات. لا يمكن إرسال قسم أو وردية أو مسمى وظيفي للزبون.

في جزء نصي واحد باسم `data` ضع JSON:

```json
{
  "OperationID":"b458177b-529b-4da1-bd24-d68230987cba",
  "OccurredAt":"2026-09-23T14:30:00+03:00",
  "TypeID":1,
  "TopicID":1,
  "BrandID":29,
  "BranchID":25,
  "Name":"اسم الزبون",
  "Mobile":"+962790001234",
  "Email":"customer@example.com",
  "Title":"ملاحظة حول الخدمة",
  "Details":"تفاصيل الشكوى أو الاقتراح",
  "DiscloseIdentity":true
}
```

المعرفات أمثلة؛ تؤخذ القيم الفعلية من `/options`. أضف الملفات الاختيارية كأجزاء متكررة بالاسم `files`. لا يوجد طلب منفصل لرفع الملفات بعد إنشاء الطلب، ولا يوجد business code مطلوب من التطبيق لتحديد المستلمين أو كتابة السجلات.

الحدود: الاسم 200 حرف، رقم التواصل 30 حرفًا بصيغة رقم هاتف يحتوي 7–15 رقمًا، البريد 254، العنوان 300، التفاصيل 10000. المرفقات PDF أو PNG/JPG/JPEG/GIF، خمسة ملفات بحد أقصى 10MiB لكل ملف، وصور حتى 20 مليون بكسل. تُعاد معالجة الصور إلى PNG مثل API الموظفين، وتبقى المرفقات في التخزين الخاص المشترك.

استجابة النجاح:

```json
{
  "Success":true,
  "Data":{
    "RequestID":1045,
    "SourceType":2,
    "Replayed":false,
    "Message":"تم تقديم طلبك بنجاح إلى إدارة النظام."
  }
}
```

## منع التكرار والأحداث

ولّد UUID جديدًا في `OperationID` لكل تقديم جديد. عند انقطاع الشبكة أعد **الرقم والبيانات والتاريخ والملفات نفسها**. ترجع المحاولة المتكررة `Replayed=true` ورقم الطلب السابق دون مضاعفة الطلب أو المرفقات أو الإشعارات. تغيير المحتوى مع رقم العملية نفسه يعيد `409 OPERATION_REUSED`.

`OccurredAt` وقت التقديم الفعلي من الجهاز بصيغة ISO 8601 مع المنطقة الزمنية. يخزن API وقت الجهاز ووقت استقبال الخادم منفصلين، ويسجل تقديم الزبون بنفسه ويربطه بمجموعة سير العمل. لا توجد API لاستقبال سجلات يكتبها الزبون.

## الحماية والأخطاء

واجهة الزبون تتيح الخيارات والتقديم فقط. مشاهدة الطلب والمرفقات والإجراءات تتطلب جلسة موظف صالح وصلاحية على ذلك الطلب عبر الواجهات الداخلية الحالية. لا يُستخدم رقم الطلب أو `OperationID` كرابط لقراءة بيانات الزبون.

يوجد حد محاولات من الاتصال نفسه: **10 محاولات تقديم في الساعة**، و**120 طلب خيارات في الدقيقة**. يشمل محاولات التقديم غير الصحيحة والمتكررة؛ يحفظ العدّاد في SQL ليعمل عبر نسخ التطبيق وإعادة التشغيل. عند التجاوز تعاد `429 RATE_LIMIT` وترويسة `Retry-After` بالثواني. حد IP لا يُثبت هوية الزبون أو ملكيته لرقم الهاتف؛ التقديم دون تسجيل دخول كما تم اعتماده.

يعتمد المحدد على عنوان الاتصال الفعلي ولا يثق بترويسات `X-Forwarded-For`. إذا نُشر التطبيق خلف proxy فستشترك اتصالاته في الحد ما لم يضبط مسؤول الاستضافة نقل عنوان العميل عبر آلية موثوقة. المضيف الذي لا يوفر عنوان الاتصال يستخدم حصة مشتركة.

صيغة الخطأ مثل API الموظفين:

```json
{"Success":false,"Error":{"Code":"BUSINESS_RULE","Message":"اختر فرعًا فعالًا يتبع العلامة التجارية المحددة."}}
```

أهم الحالات: `400` بيانات أو ملف غير صالح، `403` استخدام HTTP، `409` تعارض رقم العملية أو طلب إعادة المحاولة، `413` تجاوز الملفات، `415` صيغة غير multipart، `429` تجاوز المحاولات، `500` خطأ خادم. قد ترفض الاستضافة الأجسام الكبيرة قبل API برسالة غير JSON.

## ظهور الطلب لدى الإدارة

- يظهر المصدر «زبون» في المتابعة والتقارير والإحصائيات الحالية.
- تتاح العلامة والفرع وبيانات التواصل المسموح بعرضها والمرفقات ومخطط السير من التفاصيل الحالية.
- كل مدير نظام مستلم يرى الطلب. أول إجراء ناجح يحسمه، وتُمنع الإجراءات لدى الباقين كما في طلب الموظف.
- الإغلاق يتطلب الشروحات، ويُحفظ اسم الموظف المنفذ الحقيقي. إذا أتاح CMS التحويل لاحقًا، يستخدم فرع وعلامة الطلب المحفوظين لتحديد المديرين.
- تُرسل الإشعارات الداخلية لحسابات الموظفين المستلمين فقط. لا تُرسل رسائل SMS أو بريد تلقائية للزبون ضمن هذه الإضافة، ولا توجد متابعة عامة للزبون.

## تغييرات قاعدة البيانات والنشر

الترقية `Employee_Feedback/009_CustomerSupport.sql` تجعل `EmployeeID` اختياريًا لطلبات الزبائن فقط، مع قيد يبقيه إلزاميًا للموظفين. يبقى ارتباطه بجدول الموظفين عند وجود قيمة. لا تنشئ موظفًا وهميًا للزبون.

يسمح سير العمل بـ`SenderID=NULL` عند تقديم الزبون، وبـ`ReceiverID=NULL` عند الإغلاق الموجّه لمقدم الطلب الخارجي. يُعرف الزبون من سجل الطلب المرتبط، وتعرض الإجراءات المخزنة بياناته المسموح عرضها. تبقى معرفات الموظفين إلزامية للتحويل، ويظل منفذ الإغلاق موظفًا حقيقيًا. عُدّلت استعلامات المتابعة والتفاصيل والتوجيه والسجلات للتعامل مع هذه الحالة دون تغيير تواقيع إجراءات الموظفين.

ترقية `Mobile_API/004_CustomerFeedback.sql` تضيف سجل منع التكرار وتوقيت التقديم `Customer_Feedback_Submissions` وعدّاد الحماية `Customer_Feedback_RateLimits`. لا تتغير صلاحيات CMS أو الطلبات الموجودة.

بعد ترقيات الموظفين الحالية، شغّل `Apply-CustomerFeedback.ps1` لتطبيق الملفين في معاملة واحدة، ثم ابنِ وانشر مشروع API. يستخدم المرفقات إعداد `MobileApi.FeedbackStoragePath` الحالي. API الزبائن منفصلة عن مسار الموظفين؛ لا تحتاج تطبيقات الموظفين إلى تغيير طلباتها.

للاستيراد: `Customer-Feedback.openapi.json` و`Prosto-Customer-Feedback.postman_collection.json`. حدّث `baseUrl` إلى عنوان HTTPS المنشور. تجهيز الكود والنسخة المحلية لا يعني النشر على خادم خارجي.
