# اعتماد أجهزة تطبيق الهاتف

المرجع المعتمد — 2026-09-24. قواعد العمل تُنفّذ في API وقاعدة البيانات؛ التطبيق يرسل بيانات الدخول والجهاز ويعرض النتيجة.

## السياسة

- أول تسجيل دخول ناجح يعتمد جهازًا واحدًا تلقائيًا. يُستخرج ID الموظف ورقمه الوظيفي من الحساب المصادق عليه.
- الأجهزة الأخرى لا تحصل على توكن قبل موافقة مدير النظام. عدد الأجهزة المسموح بها هو عدد الأجهزة المعتمدة فعليًا؛ الموافقة على جهاز إضافي لا تسمح تلقائيًا بأي جهاز لاحق.
- لكل دخول ناجح توكن مستقل، مع نسخة من معلومات الموظف والجهاز وإصدار التطبيق وMAC عند توفره.
- إلغاء جهاز يبطل جميع توكناته فورًا عند الاستدعاء التالي. إعادة اعتماده تتطلب تسجيل دخول جديد؛ لا تعود التوكنات الملغاة للعمل.
- تسجيل الخروج يلغي التوكن الحالي فقط، ولا يلغي اعتماد الجهاز.
- اعتماد الجهاز مرتبط بالموظف؛ صلاحيات الشكاوى وباقي واجهات الموظفين تبقى مستخرجة من الحساب والتوكن.
- واجهات الزبائن العامة مستقلة ولا تتطلب تسجيل جهاز.

## خيارات مدير النظام الثلاثة

| الخيار | النتيجة |
|---|---|
| الموافقة وإلغاء الأجهزة القديمة | اعتماد الجهاز المطلوب وإلغاء كل الأجهزة الأخرى وكل جلسات الموظف القديمة |
| الموافقة مع الإبقاء على الأجهزة | اعتماد الجهاز المطلوب مع استمرار الأجهزة والجلسات المعتمدة سابقًا |
| إلغاء الجميع والسماح بجهاز عند الدخول التالي | إلغاء جميع الأجهزة والجلسات، وإلغاء الطلبات المعلقة، ثم اعتماد أول جهاز يستخدم بيانات دخول صحيحة |

تتوفر أيضًا إمكانية رفض طلب، أو إلغاء جهاز واحد. إلغاء جهاز واحد لا يفتح التسجيل التلقائي لجهاز آخر، حتى لو لم يتبق جهاز مسموح.

قرارات الموافقة تعتمد طلبًا معلقًا بعينه؛ إذا عالجه مسؤول آخر تعرض الشاشة رسالة تحديث الحالة. تُنفّذ القرارات وتسجيل الدخول في معاملات متسلسلة لكل موظف؛ عند تزامن محاولتين بعد إعادة التعيين يعتمد جهاز واحد فقط.

## واجهات التطبيق

جميع المسارات HTTPS. بيانات الدخول لا تُرسل في عنوان URL. لا ترسل EmployeeID لتحديد صاحب الطلب.

| المسار | الاستخدام | المصادقة |
|---|---|---|
| POST /api/Users/Login | تسجيل الدخول وإصدار التوكن إذا كان الجهاز مسموحًا | بيانات الدخول والجهاز |
| POST /api/Users/AddNewDevices | تقديم طلب اعتماد الجهاز الجديد أو إعادة نفس الطلب المعلق | بيانات الدخول والجهاز؛ لا يحتاج Bearer ولا يصدر توكن |
| POST /api/v1/devices/status | الاستعلام عن حالة هذا الجهاز لهذا الموظف | بيانات الدخول والجهاز؛ لا يصدر توكن |

المسارات الثلاثة تستخدم نموذجًا واحدًا، وتفاصيل حدود الحقول في [Device-Login-API.md](Device-Login-API.md):

```json
{
  "Username": "employee-username",
  "Password": "employee-password",
  "AppVersion": "1.0.0",
  "AppBuild": "100",
  "Device": {
    "DeviceID": "persistent-installation-uuid",
    "Platform": "Android",
    "Manufacturer": "Samsung",
    "Model": "SM-A556E",
    "OSVersion": "14",
    "MACID": "AA:BB:CC:DD:EE:01"
  }
}
```

أرسل `Device.MACID` الحقيقي عند توفره في طلب `POST /api/Users/AddNewDevices`؛ يقبل الصيغة الموحّدة مثل `AA:BB:CC:DD:EE:01`. الحقل اختياري عند عدم توفر MAC، ويُحفظ ضمن بيانات الجهاز. قيمة المثال توضيحية فقط.

نجاح تقديم طلب أو الاستعلام عنه:

```json
{
  "Success": true,
  "Data": {
    "RequestID": 42,
    "Status": "Pending",
    "CanLogin": false,
    "CreatedUtc": "2026-09-24T17:00:00Z",
    "DecidedUtc": null
  }
}
```

الحالات: NotRequested، Pending، Approved، Rejected، Cancelled. RequestID وأوقات القرار قد تكون null. CanLogin يصف السياسة الحالية؛ قد يتغير القرار قبل محاولة الدخول، ولذلك Users/Login هو الحكم النهائي. بيانات الاعتماد غير الصحيحة أو الحساب غير الفعال تعيد 401 دون كشف حالة الأجهزة.

عند محاولة الدخول بجهاز غير معتمد:

```json
{
  "Success": false,
  "Error": {
    "Code": "DEVICE_APPROVAL_REQUIRED",
    "Message": "لا يمكنك تسجيل الدخول من جهاز غير معتمد. يمكنك إرسال طلب للسماح بهذا الجهاز إلى مدير النظام."
  }
}
```

الاستجابة HTTP 403 ولا تحتوي توكن. يعرض التطبيق زر طلب اعتماد الجهاز؛ بعد الموافقة يعيد الموظف تسجيل الدخول. عند الاستعلام بعد رفض سابق يسمح إرسال طلب جديد مع الاحتفاظ بالطلب السابق. يُعاد الطلب المعلق نفسه عند تكرار إرساله، ويوجد حد خمسة طلبات معلقة للموظف (429 DEVICE_REQUEST_LIMIT).

الرمز الناتج من Users/Login يُحفظ في التخزين الآمن ويُرسل مع واجهات الموظف:

```http
Authorization: Bearer <AccessToken>
```

توكن جهاز ملغى يعيد 401 SESSION_INVALID. يحذفه التطبيق ويعرض تسجيل الدخول. لا تُخزن كلمة المرور لأغراض الاستعلام الدوري؛ يمكن طلبها من المستخدم عند التحقق من القرار، أو تجربة تسجيل الدخول مجددًا.

## إدارة الموظفين والتصميم

من Modules/Users/ManageUsers.aspx:

- مؤشرات إجمالي الأجهزة المسموحة وطلبات الموافقة والموظفين الذين لديهم أكثر من جهاز.
- مرشح للموظفين ذوي الطلبات المعلقة، وزر إدارة الأجهزة لكل موظف مع عدد الطلبات.
- نافذة مركزية تعرض اسم الموظف ورقمه الوظيفي وID، مع تبويبات: طلبات الموافقة، الأجهزة المسجلة، سجل القرارات.
- معلومات الجهاز تشمل المعرّف والمنصة والطراز والشركة والنظام وإصدار التطبيق ورقم البناء وMAC إن توفر وتاريخ التسجيل وآخر دخول.
- إجراءات تأكيد واضحة، وملاحظة اختيارية محفوظة مع القرار، وسجل زمني باسم منفذ الإجراء ووقته.
- التخزين UTC؛ العرض بتوقيت الأردن.

مرجع التصميم: [دليل مراجع الواجهة](../../../docs/UI-GUIDELINES.md) وصفحات app-user-list.html وapp-user-view-security.html وapp-user-view-account.html؛ بطاقات Frest وBootstrap والتبويبات والأيقونات والجدول المتجاوب ضمن القالب الحالي.

## قاعدة البيانات والأمان

| الجدول | الوظيفة |
|---|---|
| MobileApi_DevicePolicy | يحدد السماح باعتماد الجهاز عند الدخول التالي |
| MobileApi_Devices | الأجهزة وتفاصيلها وآخر معلومات دخول وحالة اعتمادها |
| MobileApi_DeviceRequests | طلبات الموافقة والقرار والمسؤول والتاريخ والملاحظة |
| MobileApi_DeviceHistory | سجل الإضافة والاعتماد والرفض والإلغاء وإعادة التعيين |
| MobileApi_Sessions | جلسات التوكن ونسخة بيانات الدخول، مرتبطة بـ DeviceRegistrationID |

لا تُحذف الأجهزة أو الطلبات القديمة. بيانات كل دخول تبقى في سجل الجلسة؛ معلومات الجهاز في سجل الأجهزة تعكس آخر دخول ناجح أو طلب اعتماد جديد. الطلب المعلق المكرر يحتفظ برقم الطلب نفسه. لا يحفظ التوكن الخام ولا كلمة المرور في جداول الأجهزة أو السجلات.

إجراءات إدارة الأجهزة تتحقق من أن المنفذ مدير نظام فعال وغير محذوف، وتتحقق من تبعية الجهاز والطلب للموظف. صفحة الإدارة تستخدم ViewState مرتبطًا بالجلسة. لا توجد واجهة عامة تسمح بالموافقة على جهاز.

DeviceID معرّف تثبيت مستمر وحساس لحالة الأحرف، وليس إثباتًا ماديًا أو تشفيريًا لهوية الهاتف. بيانات الجهاز وMAC يرسلها التطبيق؛ هذا النظام يضبط الأجهزة المسجلة والتوكنات ولا يتضمن attestation أو مفتاحًا خاصًا مربوطًا بالعتاد. إعادة تثبيت التطبيق بمعرّف جديد تُعامل كجهاز جديد.

## الترقية والتشغيل

1. يلزم تطبيق 001 و002 و005 قبل 006_DeviceAccess.sql.
2. شغّل Apply-DeviceAccess.ps1 لتطبيق 006 بمعاملة واحدة، ثم انشر API وPortal المبنيين من النسخة نفسها.
3. لا تُعد تطبيق 002 أو005 منفردين بعد006؛ يعيدان تعريف إجراءات الدخول دون سياسة الأجهزة.
4. الترقية تعتمد أقدم جهاز معروف لكل موظف من سجلات الدخول الموجودة، وتحتفظ بالأجهزة الأخرى كغير مسموحة وتلغي توكناتها. الجلسات التي لا تملك معلومات جهاز تُلغى، وأصحابها يستطيعون اعتماد جهاز عند الدخول التالي إذا لم يوجد جهاز معروف لهم.
5. الترقية قابلة لإعادة التنفيذ؛ لا تعيد اعتماد أجهزة سبق إلغاؤها.

ملفات تسليم مطور الهاتف: [OpenAPI](Mobile-Login.openapi.json)، [Postman](Prosto-Mobile.postman_collection.json). اختبارات Test-MobileApi.ps1 على قاعدة معزولة تغطي الموافقة والإلغاء والتحقق من التوكن والتزامن؛ Test-FeedbackApi.ps1 يغطي عدم تأثر الشكاوى وواجهات الزبائن.

## التحقق المحلي

- نجح بناء API وPortal وتجميع ManageUsers.aspx.
- نجحت 85 حالة في اختبارات الدخول والأجهزة، و86 حالة في اختبارات الشكاوى والزبائن، وفحص مستقل لتحديث معلومات الجهاز عند إعادة طلب الاعتماد.
- روجعت نافذة الإدارة وتبويبات الطلبات والأجهزة والسجل الزمني في المتصفح ببيانات معزولة، بعرض الحاسوب و390px.
- طُبقت الترقية محليًا ونُشرت الملفات المبنية مع نسخ احتياطية للملفات السابقة والتحقق من SHA256. النشر على خادم خارجي مستقل عن هذا التسليم.
