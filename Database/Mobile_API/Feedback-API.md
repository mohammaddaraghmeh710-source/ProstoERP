# واجهات الشكاوى والاقتراحات لتطبيق الهاتف

هذه الواجهات للشكاوى والاقتراحات فقط. تستخدم قواعد العمل وإجراءات SQL نفسها المستخدمة في الموقع، والصلاحيات والأنواع والمواضيع المعرفة في إدارة النظام. لا تشمل المراسلات أو إحصائيات الإدارة أو السجلات العامة.

تقديم الزبائن له [API مستقلة](Customer-Feedback-API.md) دون تسجيل دخول. تبقى الواجهات هنا موثّقة بهوية الموظف، وتتيح للمستلمين المصرح لهم معالجة طلبات الموظفين والزبائن. `SourceType=1` للموظف و`2` للزبون، وتظهر العلامة والفرع والتواصل المسموح بعرضه في التفاصيل.

## الاتصال والهوية

- العنوان الأساسي: `https://<API-HOST>/api/v1/feedback`؛ يحدد مسؤول الاستضافة عنوان HTTPS الفعلي.
- تسجيل الدخول الحالي: `POST /api/Users/Login` ببيانات `Username` و`Password` و`AppVersion` و`Device` حسب [توثيق تسجيل الجهاز](Device-Login-API.md).
- أرسل `Authorization: Bearer <AccessToken>` و`Accept: application/json` في كل طلب، بما في ذلك تحميل المرفقات.
- `EmployeeNumber` هو `Data.User.Employee_Number` الناتج من تسجيل الدخول. API يطابقه مع صاحب التوكن. لا تستخدم `Data.User.ID` مكانه، ولا يمكن انتحال موظف بتغيير الرقم.
- تواريخ الاستجابة UTC. تواريخ الهاتف بصيغة ISO 8601 تشمل المنطقة الزمنية، مثل `2026-09-23T14:30:00+03:00`. يرفض الوقت الذي يتجاوز ساعة الخادم بأكثر من خمس دقائق، أو يسبق سنة 2000.
- النتائج لا تُخزّن في الكاش. حسابات الموظفين الموقوفة والجلسات المنتهية تُرفض وفق آلية تسجيل الدخول الحالية.

## الواجهات الثماني

| الطريقة والمسار | الغرض |
|---|---|
| `GET /options?employeeNumber=...&type=0` | الأنواع الفعالة، مواضيع علامة الموظف التجارية، أنواع المستلمين، الصلاحيات، الحالات وحدود المرفقات والنصوص. `type=0` يعيد جميع المواضيع المتاحة. |
| `POST /routing-preview` | تحديد المستلمين تلقائيًا وإرجاع `IsFallback` و`CanSend` ورسالة التوجيه قبل الإرسال. |
| `GET /requests?employeeNumber=...` | متابعة جميع طلبات المستخدم، العدادات الخمسة والبحث والترقيم. |
| `POST /requests` | تقديم الطلب والملفات معًا وحفظ بيانات الموظف تلقائيًا وإرجاع `RequestID`. |
| `POST /requests/{id}/open` | فتح التفاصيل المركزية وتسجيل المشاهدة وتعليم إشعارات هذا الطلب لهذا الموظف كمقروءة. |
| `POST /requests/{id}/actions` | التحويل أو الإغلاق مع الشروحات والملفات ضمن عملية واحدة. |
| `GET /attachments/{id}?employeeNumber=...&download=false` | الملف الفعلي بعد التحقق من صلاحية الوصول. استخدم الرابط الجاهز في التفاصيل. |
| `GET /notifications?employeeNumber=...` | الإشعارات وعدد غير المقروء، دون تغيير حالة القراءة. |

## خطوات التطبيق

1. يسجل المستخدم الدخول، ويحفظ التطبيق التوكن والرقم الوظيفي.
2. يعرض `/requests` متابعة الطلبات؛ زر إنشاء الطلب يعتمد `Permissions.CanSubmit` من `/options`.
3. يعرض نموذج الإنشاء الأنواع والمواضيع وأنواع المستلمين من `/options`. لا يعرض أو يرسل بيانات الموظف أو العلامة أو الفرع أو التواصل. API يسحبها من الحساب ويحفظها مع `SourceType=1`.
4. عند اختيار نوع المستلم يستدعي `/routing-preview`. يعرض رسالة التحويل إلى مدير النظام عند عدم وجود المدير المطلوب. المستلمون الفعليون يعاد التحقق منهم عند الحفظ.
5. يرسل النموذج والملفات معًا. عند `Success=true` يعرض رسالة نجاح ويعود لمتابعة الطلبات. لا يوجد رفع ملفات منفصل بعد إنشاء الطلب.
6. عند دخول المستخدم فعليًا إلى التفاصيل يستدعي `/open` مرة واحدة لكل زيارة، مع وقت الفتح. لا يستدعيه لتحميل بيانات مسبقًا في الخلفية.
7. يعرض التفاصيل والتواصل والمرفقات ومخطط السير من الاستجابة نفسها، وأزرار الإجراءات من `AllowedActions`. الموظف مقدم الطلب ليس له أي إجراء على طلبه.
8. عند الإجراء يرسل `RowVersion` الذي استلمه من آخر فتح، ونوع الإجراء، والشروحات، ونوع المستلم عند التحويل، وأي مرفقات. لا يوجد حفظ رد مستقل.

## منع التكرار وتسجيل الأحداث

كل تقديم أو فتح أو إجراء يحتاج `OperationID` جديدًا بصيغة UUID و`OccurredAt` لوقت الحدث الفعلي. عند إعادة محاولة **العملية نفسها** بسبب انقطاع الاتصال يجب إعادة الرقم والبيانات والوقت والملفات نفسها. لا تولّد UUID جديدًا لكل محاولة شبكة.

API يحتفظ ببصمة البيانات والملفات مع النتيجة. إعادة العملية المكتملة ترجع `Replayed=true` دون إنشاء طلب أو إجراء أو ملف أو مشاهدة إضافية. إعادة استخدام الرقم ببيانات أخرى تعيد `409 OPERATION_REUSED`. رقم العملية فريد على مستوى حساب المستخدم عبر واجهات التقديم والفتح والإجراءات. فتح زيارة جديدة يستخدم رقم عملية جديدًا.

الهاتف لا يرسل سجلات أو رقم منفذ داخلي أو `ActionType` رقميًا. API يستنتج المنفذ من الجلسة، ويحدد نوع الحدث من العملية الناجحة، وينفّذ سجلات النظام والإشعارات. يحفظ جدول `MobileApi_FeedbackEvents` وقت الهاتف `OccurredAt` ووقت استقبال الخادم `ReceivedUtc`، وربط المشاهدة `ViewID` أو مجموعة الإجراء `WorkflowGroupID`. الوقت المرسل من الجهاز بيانات تدقيق، وليس مرجع ترتيب الإجراءات أو حسم التزامن؛ أوقات النظام الأصلية تبقى أوقات الخادم.

## أمثلة الطلبات

المعرفات في الأمثلة توضيحية؛ استخدم القيم من تسجيل الدخول و`/options`.

### معاينة التوجيه

```json
{"EmployeeNumber":81004,"RecipientTypeID":2}
```

عند التحويل أضف `RequestID`. يسمح بمعاينة تحويل طلب فقط لمن يملك حق التحويل عليه حاليًا.

### تقديم الطلب: multipart/form-data

أرسل جزءًا نصيًا واحدًا اسمه `data` يحتوي JSON أدناه، والأجزاء الاختيارية للملفات كلها بالاسم `files`. لا تحدد multipart boundary يدويًا؛ تديرها مكتبة HTTP.

```json
{
  "EmployeeNumber":81004,
  "OperationID":"d5bccb87-4f05-44fa-b343-853f87538665",
  "OccurredAt":"2026-09-23T14:30:00+03:00",
  "TypeID":1,
  "TopicID":1,
  "Title":"ملاحظة حول بيئة العمل",
  "Details":"تفاصيل الطلب",
  "DiscloseIdentity":false,
  "RecipientTypeID":2
}
```

استجابة النجاح بعد حفظ الطلب والمرفقات:

```json
{"Success":true,"Data":{"RequestID":1044,"Replayed":false,"Message":"تم حفظ العملية بنجاح."}}
```

### فتح التفاصيل: application/json

```json
{"EmployeeNumber":81002,"OperationID":"592ac91e-dc12-4cc8-8d5d-c36e4ae547b2","OccurredAt":"2026-09-23T14:35:00+03:00"}
```

تحتوي `Data` على:

- `Request`: العنوان والتفاصيل والنوع و`TypeName` و`TypeNameEn` والحالة و`StatusTitle` والتواريخ والعلامة والفرع والبيانات المسموح عرضها و`RowVersion` بصيغة Base64 و`CanAct`. اسم النوع يظهر للطلبات السابقة حتى لو تم تعطيله لاحقًا.
- `Contact`: مصدر الطلب والعلامة والفرع و`CanViewContact` وبيانات التواصل المسموح عرضها. في الطلب المجهول تبقى بيانات التواصل والرقم الوظيفي `null` للجميع عدا صاحب الطلب، بما في ذلك مدير النظام.
- `Attachments`: `ID` و`File_Type` و`FileSize` و`GroupID` واسم محايد و`PreviewUrl` و`DownloadUrl`. `GroupID=null` للمرفقات الأصلية، وإلا يربطها بمجموعة في مخطط السير.
- `Workflow`: مجموعات التقديم والتحويل والإغلاق بالتعليق والأسماء المسموح عرضها والتاريخ. قيم العرض `ActionType`: تقديم 1، تحويل 2، إغلاق 3. لا يرسلها الهاتف لتسجيل سجل.
- `AllowedActions`: قائمة بأكواد `transfer` أو `close` وتسمياتها ومتطلبات التعليق والمستلم. تكون فارغة لصاحب الطلب والمستلم السابق والطلبات المغلقة.
- `RecipientTypes`: أنواع المستلمين المسموح التحويل لهم عندما يكون التحويل متاحًا.

### إجراء: multipart/form-data

أرسل `data` و`files` بالطريقة نفسها المستخدمة عند التقديم:

```json
{
  "EmployeeNumber":81002,
  "OperationID":"418b533e-44bb-43d5-a845-bcd099d132cc",
  "OccurredAt":"2026-09-23T14:40:00+03:00",
  "Action":"transfer",
  "Comment":"يرجى متابعة الموضوع لدى الإدارة.",
  "RowVersion":"AAAAAAAAB9E=",
  "RecipientTypeID":1
}
```

للإغلاق استخدم `Action="close"` واحذف `RecipientTypeID`. الشروحات إلزامية في الحالتين. API يتحقق من الصلاحيات مجددًا؛ أول إجراء ناجح يحسم الطلب بين جميع المستلمين الحاليين. عند `409 REQUEST_CHANGED` أعد فتح التفاصيل وأظهر الحالة الجديدة للمستخدم.

## متابعة الطلبات والإشعارات

فلاتر المتابعة: `search` في العنوان أو رقم الطلب، `type` (0 للكل)، `status` (0 الكل، 1 جديد، 2 قيد المعالجة، 3 منتهي، 4 فعال)، و`scope` من `all/sent/action/active/closed`.

الترقيم: `page` يبدأ من 1، و`pageSize` افتراضيًا 20 وبحد أقصى 100. الاستجابة `Items` و`TotalItems` و`Page` و`PageSize`. الترتيب: بحاجة لإجراء، ثم فعالة، ثم منتهية، والأحدث أولًا داخل كل مجموعة. يوجد `IsMine` و`CanAct` لكل صف.

عدادات `Counts`: `TotalRequests`، `SentRequests`، `ActiveRequests`، `ClosedRequests`، `ActionRequiredRequests`. تحترم البحث والنوع والحالة، وقبل تطبيق `scope` والترقيم، لعرض بطاقات المتابعة كاملة.

الإشعارات تستخدم `page/pageSize` و`unreadOnly=false`، وتعيد `UnreadCount` العام للمستخدم و`TotalItems` بعد فلتر القراءة و`Items`. تحتوي الرسالة على `Request_ID` و`NotificationType` و`Title` و`SendDate` و`IsRead`. لا توجد واجهة تعليم إشعارات كمقروءة؛ فتح التفاصيل هو الذي يغير ذلك.

## المرفقات

خمسة ملفات بحد أقصى، 10MiB لكل ملف. الرفع من الهاتف يدعم PDF وPNG وJPG وJPEG وGIF فقط. الصور بحد أقصى 20 مليون بكسل، يعاد حفظها PNG دون بيانات الصورة الوصفية، ثم يعاد فحص حجمها. GIF يصبح صورة ثابتة، مثل معالجة الموقع. PDF يُفحص توقيعه؛ هذا ليس فحصًا لمكافحة الفيروسات.

`PreviewUrl` يعيد بايتات الملف الفعلي مع نوعه الصحيح؛ بيانات المرفق في JSON لا تحتوي صفحات PDF أو بكسلات الصورة. `DownloadUrl` يعيد الملف للتنزيل. الرابط يحتاج Bearer صالحًا؛ إذا كان عارض PDF لا يدعم الهيدر، ينزل التطبيق الملف باستخدام عميل HTTP الموثق ثم يفتحه محليًا. لا تضع التوكن في الرابط ولا تستخدم مسار تخزين الخادم. المرفقات القديمة بصيغ أخرى تُنزّل كملفات ثنائية.

## الأخطاء

```json
{"Success":false,"Error":{"Code":"REQUEST_CHANGED","Message":"تم تحديث الطلب أو اتخاذ إجراء عليه. أعد فتح التفاصيل."}}
```

| HTTP | أمثلة |
|---|---|
| 400 | `INVALID_REQUEST`، `BUSINESS_RULE`، `INVALID_FILE`، `FILE_TYPE` |
| 401 | توكن مفقود أو جلسة غير صالحة؛ تسجيل الدخول مجددًا |
| 403 | `EMPLOYEE_MISMATCH`، `ACTION_NOT_ALLOWED`، `HTTPS_REQUIRED` |
| 404 | `NOT_FOUND`: الطلب أو المرفق غير متاح للحساب |
| 409 | `REQUEST_CHANGED`، `OPERATION_REUSED`، `RETRY_OPERATION` |
| 413 | `UPLOAD_LIMIT` |
| 415 | `MULTIPART_REQUIRED` |
| 500 | `SERVER_ERROR`؛ إعادة محاولة العملية نفسها بنفس OperationID |

قد يرفض IIS الطلبات التي تتجاوز حد الجسم قبل وصولها إلى API برسالة الاستضافة الخاصة به. لا تفترض أن استجابة كل خطأ من الشبكة تحتوي JSON.

## التشغيل والنشر

- ملفات C# في `Prosto_ERP_API/Controllers/FeedbackController.cs` و`Prosto_ERP_API/Mobile/FeedbackFiles.cs` ضمن المشروع الحالي. فهرس عقود الهاتف: [Mobile API](README.md).
- طبّق ترقيات Employee_Feedback حتى 007، وترقيات Mobile_API الحالية 001 و002 و005 للجلسات والأجهزة، ثم `003_Feedback.sql` أو `Apply-Feedback.ps1`. لدعم الزبائن طبّق ترقيتهم الموثقة أيضًا. الترقية إضافة فقط؛ لا تعيد تهيئة طلبات المستخدمين أو صلاحيات CMS.
- اضبط `MobileApi.FeedbackStoragePath` في Web.config على **المجلد الخاص نفسه الذي يستخدمه الموقع**: `Portal/App_Data/EmployeeFeedback`. يحتاج حساب تشغيل API حق القراءة والكتابة فيه. القيمة المحلية مضبوطة لهذا المشروع؛ يجب تعديلها عند النشر على خادم آخر.
- حدود Web.config: جسم طلب 51MiB؛ خمسة ملفات × 10MiB بالإضافة إلى بيانات multipart. مهلة ASP.NET ثلاث دقائق.
- انشر DLL الخاصة بالمشروع وملفات إعداداته إلى تطبيق API خلف HTTPS. لا يكفي نسخ SQL لتفعيل المسارات، ولا يُستخدم رابط موقع Portal تلقائيًا كعنوان API.
- ملفات SQL داخل معاملة واحدة. الملفات تُكتب قبل اعتماد المعاملة، وتُحذف عند فشل العملية قبل الاعتماد. في انقطاع اتصال غامض أثناء commit، يحتفظ API بالملفات تجنبًا لحذف مرفق لطلب ربما تم اعتماده؛ أعد المحاولة بنفس رقم العملية لمعرفة النتيجة. قد يبقى ملف يتيم بعد توقف العملية المفاجئ؛ لا تحذف ملفات التخزين جماعيًا.
- اختبارات `Test-FeedbackApi.ps1` تنشئ قاعدة معزولة من مخطط الجداول الأساسية فقط، وبيانات مصطنعة مرتبطة بفرع عبدالله غوشة، ثم تحذف قاعدة الاختبار ومجلد مرفقاتها. لا تعدل بيانات الموظفين الفعلية.

ملفا التسليم القابلان للاستيراد: `Feedback.openapi.json` و`Prosto-Feedback.postman_collection.json`. عدّل `baseUrl` ومتغيرات الحساب والمعرفات في Postman. عند إعادة محاولة طلب محفوظ لا تعِد توليد متغير رقم العملية أو وقتها.
