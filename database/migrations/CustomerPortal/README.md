# Customer portal deployment

Requires CRM (including organization/logo/bilingual migrations 007/008/009/010) and employee feedback migrations through `Employee_Feedback/009_CustomerSupport.sql`. Apply `001_Accounts.sql`, `002_Services.sql`, `003_Portal.sql`, `004_MobileApi.sql`, then `006_Dashboard.sql` and `007_SelfService.sql` atomically with `Apply.ps1`. Work-guide services are retired; use `../WorkGuide_Retirement/Apply.ps1` to remove old database objects with a verified full backup. Updated deployment must remove the deleted guide ASPX/module files.

Deploy the Portal/shared-library/API builds and the current Login, Customer.Master, CustomerPortal and CRM access pages. Login as customer opens `CustomerPortal/Dashboard.aspx`, using Template `pages-profile-user.html`: profile banner, own logo/default, welcome, customer/organization details and nondeleted contact cards. `Customer_Dashboard` revalidates login status, active/nondeleted CRM account and security stamp before returning only that customer's data; account IDs cannot be selected by the browser. Logo.aspx has the same customer-only boundary. No internal CRM notes, owner details or credential hashes appear in the dashboard. Same-page CRM-style offcanvas editors permit own profile contact/address/name/registration/web fields and sanitized logo upload; brand/branch/type/owner/account/login states remain administrative. Own contacts support create/edit/activate/soft delete with both Arabic and English names. Versions, identity checks and shared CRM_Write locks prevent stale or cross-account writes.

Administrators provision/reset the separate CRM customer login in the inline CRM customer editor; CustomerAccess.aspx retains credential/activity tabs. Inactive/deleted CRM accounts and disabled logins cannot authenticate or retain access through existing sessions. Changes to credentials invalidate the current security stamp. Five failed attempts lock the account for 15 minutes. Old external employee identities remain disabled and cannot be reactivated.

The web portal and `/api/v1/customer` retain login/logout/me and owned feedback creation/history/details/initial attachments. See `MOBILE-API.md` and the Postman collection. All retired `guide/*` API endpoints return 404. Feedback retains the existing administrator workflow, notifications, ownership/snapshots, attachment validation/storage and idempotent retry protection; public unauthenticated intake remains independent. Activity retains login, credential and feedback entries with explicit feedback-type labels. Reapply services after older feedback migrations that replace the composed insertion procedure.

Run `Test-CustomerPortal.ps1 -ApiBuildDirectory <API build directory>` in Windows PowerShell 5.1 against local SQL. It creates and removes an isolated database, tests account/session denial, own-profile/contact isolation, shared feedback routing and actual HTTP contracts, including deleted route responses. `Test-Dashboard.ps1` uses `CustomerPortalPageTests.cs` to execute the real ASP.NET login/page lifecycle with a normal persisted session and no identity injection. Tests never use real customer credentials or mutate application data. Build Portal and verify desktop/mobile layout. Never deploy test helpers or synthetic fixtures. Unknown SQL commit outcomes retain attachments for operational reconciliation.

## Deploy self-service on an existing database

Run `Apply-SelfService.ps1`: it creates a full COPY_ONLY/CHECKSUM backup in SQL Server's default backup directory, verifies it, records its path in workspace `tmp/customer-self-service/verified-backup.txt`, then applies CRM 009/008/010/011 and CustomerPortal 006/007/008, exports and SHA-256 verifies existing images, and finalizes CRM 012/CustomerPortal 009 in one transaction. Logos live in FileManager/CustomerLogos and only Logo_Url remains in CRM_Accounts; binary storage and the separate logo table are removed after verification. Unknown dependents abort/roll back. Existing contacts retain NULL English names until explicitly edited. Existing logins/assignments/states are not rewritten. Deploy the matching Portal/API builds and ASPX/JavaScript changes together.

Customer mutations log before/after XML atomically in Customer_Portal_Activity, using the real CRM identity and no employee substitution. Staff CRM mutations/reads keep their original log. CRM_v_Activity and the existing CRM activity page combine both sources; CustomerAccess shows per-customer history from both. Auth success/failure and web/API logout are logged; password changes record only a boolean and safe username/state snapshots. No password, salt/hash/stamp or image payload is written to audit. Log timestamps in CRM reporting use Jordan time; the legacy CustomerAccess CreatedUtc field remains UTC. No customer-facing API write endpoints are added.

`Test-CustomerPortal.ps1 -DatabaseOnly` covers SQL ownership, fields, bilingual requiredness, stale/replay denial, auth-state changes, atomic audit and legacy logo migration with its constraints. Default execution additionally runs `Test-DashboardEditing.ps1` through actual ASP.NET POST/multipart requests with ordinary customer sessions. `-ApiBuildDirectory` retains all existing customer API/retired-route integration checks. CRM `Test-CRM-TypePage.ps1 -IncludeManagement` covers employee-side regressions, including FileManager logo storage and rollback cleanup.

Customer contacts now require Arabic/English job titles as well as both names (CRM 011/customer 008); legacy untranslated values remain NULL until edited. The dashboard address field occupies a full-width row. Customer profile writes accept only a generated Logo_Url from the validated server upload; arbitrary browser paths and traversal are rejected. Include `src/Portal/FileManager/CustomerLogos/web.config` and grant the application pool read/write access to that folder. Database backup alone no longer includes logos: back up/restore the folder with the database. Existing protected logo routes/default image and API response contracts remain unchanged.

The CRM Overview activity card opens the unified activity page with customer/executor/source/date filters and readable, encoded before/after details. Owners see only allowed account activity; authentication records remain administrator-only.

Customer brand news uses `010_BrandNews.sql` (requires News/001–002 and CustomerPortal/007). The native news-list/news-details audit joins the existing activity view. Test-News.ps1 runs inside Test-CustomerPortal.ps1/Test-Dashboard.ps1 and covers direct-link, publication, brand-change, sanitation and audit behavior. No employee/mobile news endpoint changes.

Customer details match the information-page card layout and shared customer-detail.css: title/date, a language button and return link in the header, sanitized details in the body. Test-PortalFlows.ps1 verifies real administrator add/edit forms and legacy English preservation inside the disposable page-test host, whose identity module is never registered in production.
